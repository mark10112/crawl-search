# Performance — 1 November 2026

ทดสอบจริงบน Windows / Python 3.12.3 / RAM 16 GiB / 12 logical CPUs มี RTX 4060 8 GiB แต่ **ตัวเลขชุดนี้ใช้ CPU ไม่ได้ใช้ GPU** รุ่นหลัก: Crawl4AI 0.9.5, PyMuPDF 1.28.2, MCP 1.30.0, trafilatura 2.3.1 ส่วน optional Docling 2.145.0 / EasyOCR 1.7.2 ใช้แยกทดลองในต้นแบบ

Docker Desktop VM รายงาน 12 CPUs และ RAM ประมาณ 7.67 GiB Image รุ่น CPU/browser ที่สร้างได้มีขนาดประมาณ **732 MiB** ไม่รวม SearXNG image, cache, virtual disk allocation หรือ optional GPU models

- OCR แบบ Tesseract ครั้งแรกใน worker: **0.600 วินาที**, warm p50 **0.315 วินาที**
- อ่านแคชผลลัพธ์ในเครื่อง p50 ประมาณ **0.36–0.49 ms**; p95 ประมาณ **6.7–10.9 ms** ไม่รวม MCP round-trip และไม่ควรนำไปอ้างเป็นเวลาอ่านเว็บสด
- ชุดสาม URL ในเครื่อง sequential p50 **644.11 ms**, parallel p50 **634.33 ms**: ประโยชน์น้อยในชุดนี้ เพราะงาน browser หนึ่งงานเป็นตัวกำหนดเวลาส่วนใหญ่ ไม่พบหลักฐานให้โฆษณาว่าเร็วขึ้นสามเท่า
- Peak summed working-set/RSS ของ process tree ใน harness รุ่นส่งมอบประมาณ **0.65 GiB** ไม่รวม Docker SearXNG และอาจนับ shared pages ซ้ำ

## MCP จริง

ทดสอบ initialize/list_tools/call_tool ผ่าน stdio protocol ไม่ใช่แค่เรียกฟังก์ชันภายใน

Native Python probe รอบแรก: initialize **1.87 วินาที**, ค้นหนึ่งคำ **879 ms**, อ่าน docs ครั้งแรก **93 ms**, อ่าน docs ที่มีแคช **14 ms** ตัวเลขเป็นตัวอย่างรอบเดียวและไม่ใช่การจัดอันดับ provider

ตรวจ launcher ที่ลงทะเบียนจริงอีกครั้งหลังเพิ่ม cooldown โดยเริ่มจาก working directory อื่น: initialize **2.01 วินาที**, ค้นหนึ่งคำ **1.03 วินาที** และมีผลกลับมา, อ่าน docs **101 ms**, OCR PDF ไทยหนึ่งหน้า **2.18 วินาที**, อ่าน docs จากแคช **14 ms** การค้นหนึ่งคำกลับมาสำเร็จไม่ได้หักล้างผล stress test 9/18 และไม่ได้พิสูจน์ว่าข้อจำกัดต้นทางหายถาวร

Docker probe: initialize **3.54 วินาที**, อ่าน docs ครั้งแรก **782 ms**, อ่านแคช **4.6 ms**, OCR PDF ไทยจริงหนึ่งหน้า **5.50 วินาที** ค้นใน Docker เรียกถึง SearXNG ได้ แต่ช่วงนั้นต้นทางถูกจำกัดคำขอจึงไม่ได้ผลค้น ถือเป็น **ค้นไม่สำเร็จ** ไม่ใช่ความสำเร็จเพราะ HTTP/MCP ติดต่อได้

Docker กับ Windows probe เป็นคนละช่วงเวลาและมีสภาพแคช/CDN ต่างกัน รวมทั้ง OCR หนึ่งหน้ากับสองหน้า จึงไม่หาค่า speedup ข้ามสองสภาพแวดล้อมนี้

## ค้นหา: พบข้อจำกัดจริงเมื่อเรียกถี่

รอบอ่านเว็บจริงและรอบค้นเก็บไว้ที่ `results/release-2026-11-01/` ใช้หกคำค้นซ้ำสามรอบ รวม 18 คำขอ โดยปิด result cache ใน harness ก่อนเพิ่มระบบป้องกันการยิงซ้ำ

**มีผลค้นกลับมา 9/18 ครั้ง** การเรียกที่มีผลใช้เวลาประมาณ 0.74–1.03 วินาที p50 แยกตามคำค้น แต่ช่วงหลัง DuckDuckGo ติด CAPTCHA, Brave และ Google CSE จำกัดคำขอ/พักเอนจิน ทำให้ผลค้นว่าง การคืนผลว่างเร็วไม่นับเป็น performance ที่ดี

การแก้ในรุ่นส่งมอบหลังเก็บรอบนั้น:

- แคชคำค้นที่สำเร็จสิบนาที
- เรียกต้นทางห่างกันอย่างน้อยหนึ่งวินาทีในโปรเซสเดียว
- หากผลว่างเพราะ CAPTCHA/rate limit ให้พักหกสิบวินาที และคืน `external_search_required` ให้ agent ใช้ Native web แทน
- ไม่แอบเรียกบริการเสียเงินและไม่ยิงซ้ำไม่จำกัด

ระบบป้องกันนี้ผ่าน unit tests แต่ไม่ได้อ้างว่าแก้ข้อจำกัด IP ของเสิร์ชเอนจินได้ หรือทำให้ค้นสำเร็จ 100% และไม่ได้ยิง stress test อีกรอบเพื่อบังคับให้ผลดูดีขึ้น ตัวเลข 9/18 ข้างต้นจงใจเก็บผลล้มเหลวไว้ครบ

## การทดลอง OCR ต้นแบบ

Docling/EasyOCR ไทย–อังกฤษบนภาพทดสอบเดียวกัน ใช้ประมาณ **135 วินาทีครั้งแรก** รวมดาวน์โหลด/เริ่มโมเดล และ warm ประมาณ **21.2–21.8 วินาทีต่อหน้า** Peak process tree ใน harness ประมาณ 4.79 GiB ทั้งยังตกบางบรรทัดและไม่ผ่าน gate คำหลักไทย/อังกฤษแบบเข้มงวดที่เพิ่มภายหลัง จึงไม่ได้เลือกเป็นเส้นทางปกติ

Docling เป็น framework ไม่ใช่โมเดลเดียว; ผลนี้ไม่ได้ตัดสิน OCR engine ทุกตัวที่ Docling รองรับ ข้อมูลต้นแบบ `controlled-first` มี success labels จาก gate อังกฤษที่หลวมกว่า ต้องไม่ใช้ labels นั้นอ้างว่าครบทุกบรรทัด การปรับ gate และการแก้ Markdown escaped marker ทำก่อนเก็บรอบส่งมอบแล้ว

RapidOCR/PP-OCRv5 Thai, Typhoon OCR และ PaddleOCR-VL เป็น **ตัวเลือกที่ค้นเอกสารแล้ว ยังไม่ได้วัดบนเครื่องนี้** ดู [OCR-MODELS.md](OCR-MODELS.md)
