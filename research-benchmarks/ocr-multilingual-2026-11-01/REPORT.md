# เทียบ OCR หลายภาษาใน Docker บนเครื่องนี้

ทดสอบวันที่ 1 พฤศจิกายน 2026 บน Intel i5-12400F, RAM 16 GiB และ NVIDIA RTX 4060 VRAM 8 GiB โดยรันทีละ container ไม่ให้โมเดลแย่งทรัพยากรกัน RapidOCR ใช้ CPU/ONNX สี่ threads ส่วน PaddleOCR-VL และ LightOnOCR ใช้ GPU BF16/SDPA แบบ batch หนึ่ง ไม่มี quantization หรือ cloud inference

**ผลชุดนี้: RapidOCR เร็วและใช้ทรัพยากรน้อยที่สุด ส่วน LightOnOCR ผิดน้อยที่สุดโดยเฉลี่ย PaddleOCR-VL ใช้เวลาน้อยกว่า LightOn เล็กน้อยและทำได้ดีในหน้าไทยปนอังกฤษ**

## ผลหลัก

CER คือจำนวนการแก้ตัวอักษรเพื่อให้ตรงต้นฉบับหารด้วยจำนวนตัวอักษรต้นฉบับ ยิ่งต่ำยิ่งดี คะแนนหลักเฉลี่ยเท่ากันทั้งแปดภาษาในเอกสารสะอาด ส่วนภาพปนภาษา/ลดคุณภาพแยกไว้ด้านล่าง

| รายการ | RapidOCR 3.10 / PP-OCRv5 Mobile | PaddleOCR-VL 1.6 | LightOnOCR-2-1B |
|---|---:|---:|---:|
| CER เฉลี่ยเอกสารสะอาดแปดภาษา ↓ | **1.85%** | **0.60%** | **0.19%** |
| CER เฉลี่ยรวมทั้ง 13 ภาพ ↓ | 1.64% | 0.78% | **0.54%** |
| เวลาอ่าน warm p50 ต่อภาพ ↓ | **0.834 s** | 4.162 s | 4.553 s |
| เวลาอ่าน warm p95 ต่อภาพ ↓ | **1.359 s** | 7.031 s | 10.873 s |
| RAM สูงสุดของโปรเซส รวมช่วงโหลด ↓ | **0.83 GiB** | 2.49 GiB | 2.57 GiB |
| RAM สูงสุดเฉพาะช่วง warm ↓ | **0.83 GiB** | 1.77 GiB | 1.74 GiB |
| VRAM สูงสุดที่ Torch จัดสรรให้ tensor | ไม่ใช้ GPU inference | 1.90 GiB | 2.36 GiB |
| VRAM ทั้งการ์ดเพิ่มจากก่อนโหลดโมเดลโดยประมาณ | ~0.02 GiB ซึ่งอยู่ระดับ background fluctuation | ~2.26 GiB | ~2.79 GiB |
| คำขอที่ได้ข้อความ / ทั้งหมด | 39/39 | 39/39 | 39/39 |
| ผลที่ชนขีดจำกัด 768 tokens | 0 | 0 | 0 |

เวลา warm ไม่รวมการดาวน์โหลด โหลดโมเดล และ warmup ครั้งแรก การใช้ GPU รวมมี Windows/เดสก์ท็อปใช้ก่อนโหลดประมาณ 1.2 GiB จึงแสดงทั้ง Torch allocation และการเพิ่มจาก baseline แยกกัน RAM เป็น process-tree RSS ที่สุ่มวัดทุก 100 ms อาจนับ shared pages ซ้ำ และไม่ใช่ขนาด Docker image หรือ filesystem cache

RapidOCR เร็วกว่า Paddle ประมาณห้าเท่าใน median ของชุดนี้ แต่ได้รับชื่อภาษา/กลุ่มอักษรล่วงหน้าและเลือก recognizer ตรงภาษาไว้แล้ว ตัวเลขจึงไม่รวมเวลาตรวจภาษา ทั้งหก recognizers ที่ใช้ถูกเก็บใน RAM ร่วมกัน ส่วนสอง VLM ใช้โมเดลเดียวอ่านทุกภาษาโดยไม่ได้รับชื่อภาษาก่อนอ่าน

## การโหลดและทรัพยากร

เมื่อมีไฟล์น้ำหนักใน cache แล้ว รอบที่เก็บผลใช้เวลาโหลด Rapid ประมาณ 0.71 s, Paddle 14.06 s, LightOn 6.83 s ส่วน inference ครั้งแรกที่ไม่นับใน warm ใช้ 1.20 / 12.48 / 7.18 s ตามลำดับ การเตรียม image/ดาวน์โหลดครั้งแรกใช้เวลามากกว่านี้และมีรอบแก้ setup จึงไม่ใช้ตัวเลขเหล่านี้เปรียบเทียบความเร็วอินเทอร์เน็ตหรือระยะเวลาติดตั้งใหม่ทั้งหมด

GPU ทั้งสองโมเดลพอดีกับการ์ด 8 GiB ในชุดนี้ ไม่พบ OOM แต่ยังไม่ใช่การรับรองว่าจะพอกับภาพใหญ่กว่า บริบทที่ยาวกว่า หรือการอ่านหลายหน้าพร้อมกัน p95 ของ LightOn สูงขึ้นจากหน้าฮินดีที่ใช้ประมาณ 10–11 วินาที แม้ข้อความอ่านได้ตรงต้นฉบับ

## ใช้ผลนี้เลือกอะไร

- ถ้าเน้นปริมาณและเวลา และรู้กลุ่มภาษา: **RapidOCR** เป็นตัวเริ่มที่คุ้มที่สุด
- ถ้าต้องเลือกตัวอ่านหนักสำหรับเนื้อหาคละภาษาในชุดนี้: **LightOnOCR-2-1B** ผิดน้อยที่สุด แลกกับเวลาและ GPU มากขึ้น
- **PaddleOCR-VL** ยังคงน่าสนใจ: median เร็วกว่า LightOn ประมาณ 9% และหน้าไทยปนอังกฤษสะอาดทำได้ดีกว่า แต่ไม่มีตัวเดียวชนะทุกภาพ

ผลนี้สนับสนุนการใช้ตัวเร็วกับตัวอ่านหนักร่วมกันมากกว่าการส่งทุกหน้าเข้าตัวที่ช้าที่สุด อย่างไรก็ดี benchmark ยังไม่ได้ทดสอบกฎเลือก fallback หรือความเชื่อมั่นของ OCR ว่าจับข้อผิดพลาดได้ดีเพียงใด จึงยังไม่อ้างว่า router ที่เลือกเองจะได้ความแม่นเท่าการรู้คำตอบล่วงหน้า

## ขอบเขตของหลักฐาน

ชุดทดสอบเป็น **ภาพเอกสารควบคุมที่สร้างขึ้น 13 ภาพ**: เอกสารข้อความบล็อกเดียวแปดภาษา ภาพปนภาษาสองภาพ และภาพลดคุณภาพสามภาพ ต้นฉบับและ SHA256 อยู่ใน manifest มีการแสดงผลฟอนต์/ทิศทางข้อความผ่าน browser และตรวจ contact sheet ก่อนอ่าน ไม่ใช้ข้อความเฉลยเป็น prompt

แต่ละภาพอ่านสามรอบ รวม 117 ครั้ง การอ่านภาพเดิมซ้ำเพิ่มความเชื่อมั่นด้านเวลา ไม่เพิ่มจำนวนตัวอย่างความแม่นอิสระ ขนาดตัวอย่างยังเล็ก ไม่ครอบคลุมเอกสารประวัติศาสตร์ทั้งคลัง ลายมือ ตาราง หลายคอลัมน์ ภาพเอียง คราบกระดาษ หรือ OCR บนเอกสารยาวทั้งเล่ม

Paddle รอบนี้ใช้ checkpoint ผ่าน Transformers พร้อม prompt `OCR:` ตามเอกสารทางการสำหรับการรู้จำข้อความ ไม่ใช่บริการ PaddleOCR แบบเต็มที่เพิ่ม page-layout detector ดังนั้นยังใช้ตัดสินความสามารถจัดหน้าของ pipeline เต็มไม่ได้

มีรอบ setup ที่แยกออกก่อนเก็บผล: Rapid ขาด dependency RTL ในตอนแรก; Paddle ตัวอย่าง model-card ใช้ attribute ของ processor แบบเก่า; LightOn ถูก AutoModel เลือกเป็น Mistral3 ทำให้น้ำหนักบางส่วนไม่ตรง จึงแก้เป็นคลาส LightOn โดยตรงและตรวจ missing/unexpected keys ก่อนวัด รอบผิด setup และปัญหาการบันทึก metadata ไม่นับเป็นคะแนนโมเดล เก็บ logs แยกให้ตรวจย้อนหลังได้
